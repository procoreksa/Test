# Technical Debt Register

Produced during the production-readiness hardening pass. Purpose is
visibility, not perfection - per the brief, only P0/P1 items were fixed in
this pass; P2 items were fixed only where low-risk, localized, and clearly
beneficial. Everything below that wasn't fixed is intentionally left for
a future, separately-scoped task.

Severities: **P0 Critical** (data loss/security breach risk, fix
immediately) · **P1 High** (real risk, fix soon) · **P2 Medium** (real but
bounded risk or cost, schedule it) · **P3 Low** (cosmetic/nice-to-have).

## P0 - Critical

None found.

## P3 - Low

| # | Issue | Affected module | Recommended future action |
|---|---|---|---|
| 1 | No login rate limiting - now **three** public, unauthenticated, abuse-sensitive endpoints exist (`/login` for internal staff, `/portal/login` for tenants, and `/owner-portal/login` for owners, added by the Tenant Portal and Owner Portal respectively). Deliberately not implemented in this pass: no in-process limiter is safe across multiple server instances without shared state (Redis/similar), which this codebase has no existing infrastructure for, and a single-process in-memory limiter would give a false sense of protection in any real multi-instance deployment while adding real complexity now. All three login paths already share the mitigations that matter most given that gap: bcrypt's own cost factor slows brute force regardless of any rate limiter, and all three `authorize()` paths (`src/lib/auth.ts`, `src/lib/tenant-credentials.ts`, `src/lib/owner-credentials.ts`) return an identical generic failure for every rejection reason (wrong password, nonexistent account, inactive account), so there is no username-enumeration oracle to combine with a fast-guessing attack. | `src/lib/auth.ts` / `/login`, `src/lib/tenant-credentials.ts` / `/portal/login`, `src/lib/owner-credentials.ts` / `/owner-portal/login` | Add IP- or account-based throttling once a shared store (Redis or the hosting platform's own edge rate limiting, e.g. Render's) is available - apply it to all three login paths identically, not just the newest one. |

## Fixed this pass (for completeness - not "still open")

- Unused npm dependency `uuid` removed (zero usages anywhere in `src/`;
  the codebase's only UUID need, ZATCA's invoice UUID field, already used
  Node's built-in `crypto.randomUUID()`).
- Missing security headers added (`X-Content-Type-Options`,
  `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, HSTS in
  production).
- `scripts/check-data-integrity.ts` added - a read-only, standing tool to
  re-verify the cross-org/state-consistency/ownership-total invariants
  this document and `docs/SECURITY-REVIEW.md` describe, against real data,
  at any time in the future without writing a one-off query.
- `/api/health` added - minimal, unauthenticated, leaks nothing beyond
  "database reachable: yes/no."
